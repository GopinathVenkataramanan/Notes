# Client Solution Architecture: SaaS Replacement Discovery Pack

This pack holds the deliverables the **Client Solution Architect (SA)** gives the SaaS vendor for discovery and estimation. The context is replacing an on-premises legacy application with a vendor-hosted SaaS (COTS) product.

> Example data is used throughout: a hypothetical claims-management replacement. Replace system names, IDs, volumes and targets with your actual values before you issue the pack.

## Purpose

The pack helps the vendor understand three things well enough to produce a credible estimate:

1. **What exists today.** The legacy application, its users, its data and its integrations.
2. **What the future SaaS solution needs to look like.** The target context, integrations, security and NFRs.
3. **What needs to change, integrate, migrate or be retired.**

The target architecture in this pack is a **client-level conceptual architecture**, not the vendor's final solution design. The vendor is expected to validate it, identify gaps and produce the detailed target architecture as part of their proposal.

## Where this pack sits in the consolidated discovery pack

```
BA team ............ requirements, processes, Product Fit-Gap Matrix
Technical BA ....... application/integration/data inventories, interface specs
Client SA .......... THIS PACK (architecture, standards, NFRs, security, responsibilities)
Test team .......... test strategy, migration validation, performance/security testing
Project team ....... scope, roadmap, governance, RAID, cutover constraints
        |
        v
CONSOLIDATED DISCOVERY PACK -> VENDOR VALIDATION AND ESTIMATION -> Vendor WBS -> FINAL SAAS VENDOR COST
```

The Client SA pack references, but does not duplicate, the Technical BA's integration catalogue and data migration inventory. The link between them is the shared IDs in [13 Architecture Element Register](13-Architecture-Element-Register.md).

## Conventions

- **Element IDs:** `SYS-nnn` systems, `INT-nnn` interfaces, `DATA-nnn` data stores, `ENV-nnn` environments. They are reused in the diagrams, the Technical BA catalogues and the vendor estimation workbook.
- **Requirement IDs:** `EAS` standards, `SAR` SaaS architecture, `SEC` security, `NET` network, `OPS` operations, `NFR` non-functional, `RSK` risks, `CON` constraints, `DEC` decommissioning, `DDQ` due-diligence questions.
- **MoSCoW priority:** Must / Should / Could / Won't.
- **Vendor response codes** (used in documents 03 to 07): `C` Complies as standard, `CC` Complies with configuration, `PC` Partially complies, `NC` Does not comply, `R` Roadmap (state the date).
- **Example values** are marked *(example)*. Agree actual targets with business, security and operations stakeholders. They are not recommended contractual values.
